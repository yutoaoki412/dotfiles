# Codex Desktopのチャット名

Desktopの親チャットでは、新規・再開後の最初の依頼、主題や成果物の変更、ユーザーまたは外部の対応待ち、完了報告の直前に、現在の件名と実際の作業を照合する。短い依頼は回答時にまとめて更新してよい。

命名判断は `gpt-6.1-terra` の専用サブエージェントに委任する。親は現在の件名、このチャットで引き受けた範囲、確認済みの成果、残作業と待ち先を短くまとめて渡す。最初は `spawn_agent` で `fork_turns="none"` とモデルを明示し、同じチャットで利用できる担当は `followup_task` で再利用する。担当はツールを使わず件名案だけを返す。命名担当を含むサブエージェントにはこの委任・改名ルールを適用しない。

件名は「状態の絵文字 対象と目的」の短い日本語にする。🔵はCodexの作業中、🙋はユーザーの判断・入力・操作待ち、⏳は進行中の依頼に必要な外部の回答・処理・開始時刻待ちを表す。⏸️は今回分を終えて区切りを付け、同じチャットで続きを扱う状態。✅はこのチャットで引き受けた目的と必要な確認をすべて満たし、閉じてよい状態。

応答を終えるときは「今アーカイブしても、このチャットで引き受けた残作業や次回の実行を見失わないか」で判断する。ユーザーの判断待ちは🙋、進行中の依頼でCIなどの結果待ちは⏳を優先する。定期チャットは今回分を終えて次回もここで続けるなら⏸️、運用を終了したり別チャットへの引き継ぎを完了したりして役割を終えたら✅とする。✅への改名はアーカイブ操作を伴わない。

✅を付ける前に、会話で約束した成果物・確認・引き継ぎと、実際に済んだことを照合する。ユーザーの「OK」は、何に対する同意かを直前のやり取りから確かめる。たとえば仕様に合意しても、約束した計画書や図への反映を次回に残したなら⏸️。仕様の相談だけを引き受け、回答で目的を満たしたなら✅にできる。

「もう終わりでいいよ」「他の方が対応したのでこちらは終了」など、ユーザーがこのチャットでの対応を明確に終えた場合も✅とする。引き取られた作業や取り下げられた依頼は、終了理由として扱う。「今日はここまで、続きは明日」なら⏸️とする。

再開時や既存タイトルの整理時も同じ基準で判定する。既存の✅や最後の応答だけで完了を引き継がず、残作業が記された箇所と、その後に解消・引き継ぎが確認できる箇所まで必要な範囲で読む。続きをここで扱うと分かれば⏸️、待ち先があれば対応する絵文字に直す。履歴から状態を特定できない場合は状態の絵文字を省く。

状態だけが変わったら絵文字だけを替える。ユーザー指定の件名、【日次】、Issue番号は保つ。

分類を特定できるときは「状態の絵文字 【分類】対象と目的」とし、親は命名担当に依頼元と主題も伝える。JIRAチケットで受けた個別の取り込み依頼（列追加を含む）は【JIRAチケ】、取り込み依頼刷新PJの設計・実装・検証・進捗整理は【取り込み依頼刷新PJ】、業務をSkills化PJで業務手順を整理し、Skillを設計・実装・検証・改善する仕事は【業務をSkills化PJ】、Slackの #i3-gcp-lookerで受けた問い合わせは【問い合わせ対応】とする。複数に該当するときは個別のJIRA依頼、主題となるPJの成果物、問い合わせの順に分類を1つ選ぶ。PJはユーザーの指定や親タスクに基づいて判定する。既存のSkillを使って業務を行うだけの場合、その業務の分類を使う。参考リンク・作業ログ・投稿先として登場しただけのチャンネルは依頼元に数えない。根拠がないときは分類を省く。既存の【日次】などの用途表示は残す。

親が案を会話と照合し、差分がある場合だけ Desktop の `set_thread_title` で自分のチャットを更新する。強制終了などで古くなった表示は再開時に合わせる。

完了の返事を送る前に、短い終了の返事でも、親は対象のチャットIDと確定した件名を照合する。件名が違えば改名し、同じIDを `read_thread(includeTurns=false)` で読み戻して、保存された件名が絵文字を含めて一致することを確かめる。すでに一致していれば読み取りだけでよい。食い違う場合は最新の依頼とIDを再確認して必要な更新をやり直す。確認できない場合は、作業の終了とタイトルの反映未確認を区別して伝える。
