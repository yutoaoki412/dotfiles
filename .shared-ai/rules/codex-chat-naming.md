# Codex Desktopのチャット名

Desktopの親チャットでは、新規・再開後の最初の依頼、主題や成果物の変更、ユーザーまたは外部の対応待ち、完了報告の直前に、現在の件名と実際の作業を照合する。短い依頼は回答時にまとめて更新してよい。

命名判断は `gpt-6.1-terra` の専用サブエージェントに委任する。親は現在の件名、このチャットで引き受けた範囲、確認済みの成果、残作業と待ち先を短くまとめて渡す。最初は `spawn_agent` で `fork_turns="none"` とモデルを明示し、同じチャットで利用できる担当は `followup_task` で再利用する。担当はツールを使わず件名案だけを返す。命名担当を含むサブエージェントにはこの委任・改名ルールを適用しない。

件名は「状態の絵文字 対象と目的」の短い日本語にする。🔵はCodexの作業中、🙋はユーザーの判断・入力・操作待ち、⏳は進行中の依頼に必要な外部の回答・処理・開始時刻待ちを表す。今回の応答や作業が一区切りつき、具体的な待ち先がなければ⏸️を既定とする。単発の相談に答えたとき、成果物を渡したとき、定期チャットの今回分が済んだときも同じ。状態を決めるためだけに終了確認を求めない。

✅は次のいずれかに限る。

- ユーザーが「これでおしまい」「このタスクはもうOK」「他の方が対応したのでこちらは終了」など、このタスク全体を終える意思を示した。
- ユーザーが別セッションでの続行を指示し、残作業と必要な情報を引き継ぎ先に渡して、このチャットの役割が終わった。

「OK」が仕様や途中の成果物への同意なら、その時点の作業・待ち先に合わせる。「今日はここまで、続きは明日」なら⏸️。引き継ぎの途中も進行状況に合う状態を使う。✅への改名はアーカイブ操作を伴わない。

再開時や既存タイトルの整理時も、依頼と実際の引き継ぎを会話から確かめる。応答が済んでいても、✅の条件を確認できなければ⏸️とし、判断・外部処理を待っていれば対応する絵文字を使う。履歴が読めず状態自体を特定できない場合は状態の絵文字を省く。

状態だけが変わったら絵文字だけを替える。ユーザー指定の件名、【日次】、Issue番号は保つ。

分類を特定できるときは「状態の絵文字 【分類】対象と目的」とし、親は命名担当に依頼元と主題も伝える。JIRAチケットで受けた個別の取り込み依頼（列追加を含む）は【JIRAチケ】、取り込み依頼刷新PJの設計・実装・検証・進捗整理は【取り込み依頼刷新PJ】、業務をSkills化PJで業務手順を整理し、Skillを設計・実装・検証・改善する仕事は【業務をSkills化PJ】、Slackの #i3-gcp-lookerで受けた問い合わせは【問い合わせ対応】とする。複数に該当するときは個別のJIRA依頼、主題となるPJの成果物、問い合わせの順に分類を1つ選ぶ。PJはユーザーの指定や親タスクに基づいて判定する。既存のSkillを使って業務を行うだけの場合、その業務の分類を使う。参考リンク・作業ログ・投稿先として登場しただけのチャンネルは依頼元に数えない。根拠がないときは分類を省く。既存の【日次】などの用途表示は残す。

親が案を会話と照合し、差分がある場合だけ Desktop の `set_thread_title` で自分のチャットを更新する。強制終了などで古くなった表示は再開時に合わせる。

作業の区切りや終了を伝える前に、短い返事でも、親は対象のチャットIDと確定した件名を照合する。件名が違えば改名し、同じIDを `read_thread(includeTurns=false)` で読み戻して、保存された件名が絵文字を含めて一致することを確かめる。すでに一致していれば読み取りだけでよい。食い違う場合は最新の依頼とIDを再確認して必要な更新をやり直す。確認できない場合は、作業の終了とタイトルの反映未確認を区別して伝える。
