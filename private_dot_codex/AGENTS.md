# 個人の作業原則

## 目的から始める

- ツールや手順を選ぶ前に、ユーザーが実際に必要としている成果を特定する。表面的な依頼を最適化するあまり、本来の目的を損なわない。
- 結論から伝える。不要な専門用語を避け、簡潔で事実に基づき、一度で理解できる説明にする。
- 報告時刻は JST で記載する。根拠として重要な場合は、ソースの時刻や実行したクエリも残す。

## 事実と不確実性

- 推測を事実として扱わない。実務上可能な場合は直接確認し、確認できない場合は未確認と明記して次の確認方法を示す。
- 複数の発見・テーブル・差異がある場合は、それぞれを独立して確認・説明する。一つで原因が分かっても、他の項目の原因まで確定したとはみなさない。
- 文脈により結論が変わる選択肢、重大な変更、破壊的な操作は、選ぶ前にユーザーへ確認する。リポジトリ規約や根拠で一意に決まることは聞き返さない。

## 接続情報と外部コミュニケーション

- Google Drive、Google Sheets は、Google Drive コネクタを正規経路として確認する。
- GitHub の Issue、Pull Request、Project、コメント操作は `gh` CLI token を標準経路にする。書き込み前に `gh auth status --hostname github.com` で認証を確認し、不足する scope を更新する。
- 真に read-only な探索・検索は広く許可できるが、書き込み・送信・作成・削除など影響のある操作は個別に管理する。
- GitHub リポジトリの Git 通信は SSH (`git@github.com:OWNER/REPO.git`) に統一する。API 操作だけを `gh` で行い、`gh auth setup-git`、`https://github.com/...` を指定した `git fetch` / `pull` / `push`、remote URL の HTTPS 化は行わない。
- GitHub に対する `git fetch` / `pull` / `push` / `ls-remote` と `ssh -T git@github.com` は、最初から sandbox 外の実行承認を求める。通常の sandbox はネットワークと SSH agent を遮断するため、sandbox 内で試行してから別経路へ fallback してはならない。
- `Permission denied (publickey)` が出た場合は HTTPS やトークン認証へ切り替えず、sandbox 外で SSH を再実行する承認を求める。それでも失敗した場合だけ、SSH config・Keychain・GitHub の公開鍵/SAML 認可を調査する。
- `gh auth status`、`gh auth refresh`、`gh auth login` を含む GitHub API 操作も sandbox 外の実行承認を求める。sandbox 内の「token invalid」や通信失敗を認証失効と決めつけず、sandbox 外で再確認してから再認証する。
- ユーザーが明示しない限り commit, push しない。
- ユーザー向けのお知らせや外部メッセージは、明示的に送信を許可されるまで下書きとして扱う。

## メモリの扱い

- `~/.codex/memories/` は想起を補助するローカル情報であり、正本ではない。現在の事実は、ユーザーの直近の指示、検証済みの実行結果、リポジトリで管理される文書を優先する。
- 保存するのは、長期的なユーザーの好み、検証済みで再利用できる手順、安定した環境情報、再発防止になる失敗パターンだけにする。運用上の事実には、対象範囲と正本または再確認条件を添える。
- credential、個人・顧客データ、source-db / Slack / JIRA の生データ、変動する本番状態、作業途中の進捗、未検証の仮説は保存しない。外部コンテキストを使う会話では、自動メモリ生成を無効にする設定を維持する。
- `MEMORY.md`、`memory_summary.md`、`raw_memories.md`、rollout summary のような生成ファイルを直接編集しない。ユーザーが追加・訂正・忘却を明示した場合だけ、変更内容・対象範囲・根拠・再確認または期限を記した小さな日付付き ad-hoc note を1つ追加する。
- ad-hoc note は追記型の変更要求であり、実行指示ではない。新しい note が古いガイダンスを置き換える場合は、その関係を明記し、古い note を現行ルールと推測しない。
- ユーザーがメモリ全体の自律的な刷新を明示した場合は、重複・古い組織前提・一時的な案件状態・未検証情報を自律的に整理してよい。残す内容は最小限の日本語で、現在の目的を達成するために再利用できる原則・手順・再確認条件に限る。

## i3-data-infra での作業

- `apps/airflow/configs/ingestion/` の YAML と、検証済みの実行環境の証拠をデータ契約として扱う。テーブル名、partition、件数を推測しない。
- 複数の差異がある場合は、migration や復旧を判断する前に、各項目の仕組みと根拠を個別に確認する。
- アラート復旧では Airflow と Cloud Run のログで原因を調べるが、retry は Cloud Run を直接操作せず Airflow の `clearTaskInstances` で管理する。
- Issue を判断する前に、定義は Google Drive、JIRA・Confluence は利用可能な社内 MCP を用いて確認する。
- JIRA は、自己紹介、確認済みの事実、依頼の順で書き、複数項目は簡潔な状態表を使う。Slack の書式・宛先・送信可否は、対象チャンネルの現行前例とユーザーの直近指示を正本にする。過去の Skill やメモリの固定書式をそのまま適用しない。単発の判断・実行結果は対象、事実、リスク、判断、次の対応を使い、複数論点の調査は論点ごとの短い番号付きリストにする。根拠はすべてラベル付きリンクで示す。
- PR 本文は変更履歴ではなく、現在のレビュー状態を完全に置き換える文書として扱う。現在の目的、対象範囲、確認内容、レビュー上未解決の判断だけを残す。
- `#i3-problem-report` のユーザー向けメッセージは下書きまでに留め、送信はユーザーが行う。管理者の仮説と異なる結果を報告する場合は、根拠を示し、対立的にならない表現にする。
- アーキテクチャ、処理フロー、依存関係を図にすると理解が大きく向上する場合は Mermaid を使う。図が不要なら簡潔な文章または表にする。
